## 1. Story statement

**As** the portal's architect-of-record,
**I want** the three candidate approaches to a mature mobile lightbox — Yet Another React Lightbox + Zoom, PhotoSwipe 5.4.x, and extending the in-house `ImageFullscreenViewer` — scored against measured bundle cost, real integration cost at both existing mounts, WAI-ARIA/WCAG 2.2 conformance, and gesture quality on a physical Android phone,
**so that** Story 53.2 implements a *chosen* approach with its trade-offs already priced, and G26-LIB closes on evidence rather than on the research preference recorded in the operator packet.

**Adoption is not pre-decided.** The operator packet records a research *preference* for option 1 with option 2 as plan B. Decision BA (`architecture.md:3367`) converts that into a *procedure*, not a dependency: *"This decision therefore fixes a procedure, not a dependency."* Option 3 must be scored as seriously as the two libraries — `architecture.md:3369`: *"Story 48.1 proved the component is small, understood, and now covered by a geometry regression suite. A dependency must earn its place."*

## 3. Design decisions

### D-1 — The deliverable is one artifact at one path, and it is the *only* file this story may add

Output: **`_bmad-output/implementation-artifacts/spec-e53-1-lightbox-adoption-recommendation.md`**.

Chosen because: `_bmad-output/implementation-artifacts/*.md` at the top level is a **git-tracked** surface (AGENTS.md § BMAD artifact tracking), so 53.2/53.3 and any external reviewer on a fresh clone can read it; and it matches the naming already used for this epic's shipped predecessor, `spec-e48-1-mobile-fullscreen-containment.md`. It is *not* `docs/design/` (that is the human product-spec surface) and *not* `docs/plans/` (gitignored).

### D-2 — Bundle-size delta is **measured**, in a throwaway worktree, and nothing installed ever reaches the story branch

`epics.md:4571` says *measured* bundle-size delta, so an estimate, a bundlephobia screenshot, or a README claim does not satisfy AC-2. But the story may not land a dependency — 53.2 owns that call, and it is not made yet.

Protocol (all commands from `apps/web/`):

1. **Baseline.** At `513f4bd`, `npm ci && npm run build`. Record, from the Vite output, every emitted `dist/assets/*.js` with raw + gzip bytes; identify the chunk carrying `ImageFullscreenViewer` (it is lazy-split, so it is its own chunk — confirm by name/content, do not assume). Record total JS raw + gzip.
2. **Candidate probe.** `git worktree add` a **throwaway** worktree per candidate. Install the candidate there (`npm i yet-another-react-lightbox@3.32.0` / `npm i photoswipe@5.4.4`). Add a **temporary probe module** that is dynamically imported from the same place the viewer barrel is, and that imports exactly the API surface a real integration would use (for YARL: the lightbox + the Zoom plugin **and the Thumbnails plugin** — see the amendment below; for PhotoSwipe: `PhotoSwipeLightbox` + `photoswipe.css`). Build. Diff against step 1.

   *Amended 2026-07-29 (review-ACCEPTED, non-blocking):* this recipe originally named only "the lightbox + the Zoom plugin" for YARL. A real integration must also satisfy **I-1**'s thumb renderer and **I-4**'s strip testids, which requires YARL's in-package **Thumbnails** plugin. Both configurations were measured and are both reported (**1a** = Zoom only, **1b** = Zoom + Thumbnails), with 1b nominated as the figure a real integration pays. Thumbnails is a plugin *of* `yet-another-react-lightbox@3.32.0`, not a separate package, so this is a **within-option-1 variant**, not a fourth option — § 5's "exactly three options" rule is intact and `yet-another-react-lightbox-lite` stays excluded by rule.
   - The probe isolates **tree-shaken dependency cost under this repo's actual Vite/Rollup config** — which is the number 53.2 will actually pay, and is not knowable from a package's published size.
   - CSS counts. PhotoSwipe ships a required stylesheet; YARL ships CSS too. Report JS and CSS separately; do not fold them.
3. **Option 3.** Dependency delta is **0 bytes** — `@radix-ui/react-dialog ^1.1.2` is already a direct dependency **paid for app-wide** — every dialog in the app goes through `ui/dialog.tsx`, so option 3 adds no supply-chain surface and no new vendor bytes to any chunk. Do not manufacture a false-precision number by writing throwaway zoom code.
4. **Delete every throwaway worktree.** `git worktree remove --force`. The story branch's `package.json` and `package-lock.json` must be byte-identical to `513f4bd` at the end (AC-6).

### D-4 — Criterion 4 is **operator evidence**; the recommendation ships *provisional* and G26-LIB does **not** close here

The dev agent has no physical Android phone. `epics.md:4579` forbids simulating or inferring this evidence. Fabricating a gesture-quality score is the failure mode this decision exists to prevent.

Resolution — **zero-code, zero-deploy**, because all three options are already reachable from a phone today:

| Option | What the operator opens on the physical Android Chrome device |
|---|---|
| 1 — YARL + Zoom | the vendor's own Zoom plugin demo on `yet-another-react-lightbox.com` |
| 2 — PhotoSwipe 5.4.x | the vendor's demo gallery on `photoswipe.com` |
| 3 — in-house viewer | the **live portal**, `https://3d.ezop.ddns.net` → any `/catalog/<id>` with photos → fullscreen viewer (this is the deployed 48.1 code) |

The story writes the protocol (same device, same browser, same session, same ordered gesture checklist, an explicit note that option 3 currently has **no** pinch/pan so what is being judged for it is the *existing* swipe/tap layer and the toolbar/close reachability) and leaves the result cells **empty and visibly marked unfilled**. Disclose the confounder in the artifact: vendor demo pages do not run this repo's image pipeline or auth, so **gesture feel transfers; load behaviour does not**.

Consequence, stated in the artifact: the recommendation is **PROVISIONAL — pending physical Android Chrome evidence**. `implementation-readiness-report-2026-07-26.md:205` makes G26-LIB close on *"53.1 recommendation **plus** physical Android evidence"*; this story delivers the first conjunct and the instrument for the second. **Closing G26-LIB is the operator's act, not this story's.**

### D-5 — The recommendation must be a ranked call with a named runner-up and a reversal trigger

*"Written recommendation"* means a decision, not a comparison table with an open ending. The artifact must state: the recommended option; the runner-up; the specific evidence that would flip the call (e.g. *"if I-1 comes back **blocked** for option 2, option 2 is eliminated regardless of bundle score"*); and — if the recommendation is option 3 — the explicit list of what 53.2 then has to build in-house.

Weighting is recorded, not implied: the four criteria are **not** equal. I-1 (auth-boundary expressibility) is a **hard gate** — an option that cannot express it is eliminated on correctness, not merely down-scored, because failing it breaks NFR10-SHARE-SECURITY-1. Bundle size is a **tiebreaker**, not a gate, in an app that already ships Three.js. State the weighting in the artifact so a reader can disagree with the *weights* rather than having to reverse-engineer them.

### D-6 — Nothing about this story touches i18n, a11y assertions, or visual baselines

`epics.md:4549` imposes per-story i18n/a11y/visual merge-gate ownership on **every story in E52**, and `epics.md:4575` imposes it on **53.2**. `epics.md:4571` explicitly exempts 53.1: *"this story owns no i18n/a11y/visual surface of its own."* A doc-only diff cannot regress a baseline. The full `check-all.sh` is therefore **not** this story's merge gate — see §7 for what is.

## 4. Acceptance Criteria

**AC-1 — Exactly three options, each scored.**
Given the artifact at `spec-e53-1-lightbox-adoption-recommendation.md`, when it is read, then it scores **exactly** (1) Yet Another React Lightbox + Zoom plugin, (2) PhotoSwipe 5.4.x, (3) extending the in-house `ImageFullscreenViewer` — no fourth option, no option silently dropped, and option 3 carries the same depth of evidence as options 1 and 2. The resolved versions actually measured are recorded verbatim.

**AC-2 — Bundle-size delta is measured, per D-2, and reported per chunk.**
Given the measurement protocol in D-2 was executed, when the artifact reports bundle cost, then for each of options 1 and 2 it gives raw **and** gzip bytes, **JS and CSS separately**, as a delta against the `513f4bd` baseline, and names which emitted chunk absorbed the delta (main vs the lazy viewer chunk). Option 3's dependency delta is reported as **0 bytes** with its first-party-source cost labelled an **estimate**. Every number is accompanied by the command that produced it. No number is sourced from a package registry, a README, or bundlephobia.

**AC-3 — Integration cost is scored against I-1…I-4 as a table.**
Given D-3's four obligations, when the artifact reports integration cost, then each option × each obligation is marked **native / adapter / blocked** with a file+line or vendor-doc anchor. I-1 (`renderImage`/`renderThumb` blob-renderer expressibility at both mounts) is explicitly flagged as the **hard gate**, and any option marked **blocked** on I-1 is stated as eliminated. The `renderImage`/`renderThumb` auth boundaries are **described and priced, never modified** — this story changes no code.

**AC-4 — Accessibility is scored as a delta against the shipped Radix baseline.**
Given the shipped viewer already has Radix modal semantics, focus trap, return focus, Escape, `aria-label`s and a sr-only `DialogTitle`, when the artifact scores accessibility, then it scores each option against **WAI-ARIA APG modal-dialog** semantics, **focus trap + return focus**, and **visible zoom controls satisfying WCAG 2.2 SC 2.5.1 (Pointer Gestures) and SC 2.5.7 (Dragging Movements) without relying on pinch** — as a *delta* from that baseline, not from zero.
