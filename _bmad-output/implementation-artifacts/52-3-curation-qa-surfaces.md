## 1. Story statement

**As** the portal administrator,
**I want** one advisory panel on `/admin/categories` that tells me, in six named checks, where the browse vocabulary has drifted — models with no category or with too many, categories that are empty or behaving like a narrow tag, category labels colliding with tag labels, and user-facing tags with no group,
**so that** I can keep the taxonomy honest by my own judgement — without the portal ever auto-correcting anything, inferring category membership from tags, or calling a valid state an error.

**FR mapping.**

| FR | What this story must make true |
|---|---|
| **FR26-ADMIN-2** | All six checks are surfaced, **advisory only**. No automatic synchronization, no membership inference from tags, no suggestion ever auto-applied. Every row is a warning + a link to the fix, never a fix. |
| **FR26-CAT-2** | A zero-category model is surfaced as curation work, **never** as a defect, and never on a member-facing surface. The panel row is a **count** that links into 52.2's shipped queue — it does not rebuild that list. |
| **FR26-CAT-3** | The "unusually many" threshold is the **1–3 advisory norm**, expressed as one shared constant so the QA panel and the shipped replace-set editor can never disagree. Nothing here blocks a write; the panel performs no write at all. |
| **FR26-GOV-1** | "Similar Category/Tag labels are permitted only with an explicitly recorded semantic distinction" gets a surface: the label-collision check makes the similarity visible so the admin can record the distinction or rename. |

## 3. Design decisions

### D-1 — Exactly one additive backend read, and why the other five checks get none

Five of the six checks are pure client-side derivations over data `/admin/categories` already loads or can load from a shipped, unbounded, admin-appropriate endpoint (§2). Adding backend for them would be invention.

Check 2 is different. No shipped contract can produce either the *set* of over-categorized models or the per-model *count* the UX row requires ("Model „Wazon spiralny" ma **4** kategorie", `EXPERIENCE.md:477`).

Decision AY's escalation rule (`architecture.md:3332`) is applied here **by analogy, and that is stated rather than glossed**: its literal text is step (4) of a resolution order written for Story 50.3's suggestion-pill group label, and it ends with a prohibition specific to that surface ("never a second suggestion endpoint"). What generalizes is the *principle* it encodes — exhaust the shipped contracts first, and only then propose the **smallest additive contract extension** — which is the same test B-1 is held to below. B-1 is not a suggestion endpoint and the 50.3 prohibition does not reach it. If a reviewer reads the rule as strictly 50.3-scoped, then B-1 needs Ask-First ratification rather than this story's own authority; the exhaustion evidence in §2 is identical either way.

**B-1 — `GET /api/admin/models/over-categorized`.**

- Query params: `min_categories: int = Query(default=4, ge=1, le=50)`, `limit: int = Query(default=50, ge=1, le=200)`.
- Response: `OverCategorizedResponse { items: list[OverCategorizedModelRead], total: int }` where `OverCategorizedModelRead = {model_id, slug, name_en, name_pl, category_count}`.
- Order: `(category_count DESC, slug ASC)` — worst first, deterministically.
- Auth: `current_admin`. Pure read: **no audit row, no mutation.**
- Implementation: the mirror of `_browse_category_model_counts` — `select(ModelBrowseCategory.model_id, func.count()).join(Model).where(Model.deleted_at.is_(None)).group_by(ModelBrowseCategory.model_id).having(func.count() >= min_categories)`, plus a `count()` over that subquery for `total`. **Two statements, constant** regardless of catalogue or assignment cardinality.

**Why a dedicated admin route rather than a param on `GET /api/models`.** `uncategorized` (52.2 B-2) could be a boolean predicate on the public list because the answer is *which models*, and `ModelSummary` already carries everything the queue renders. Here the answer is *which models **and how many each***, and `ModelSummary` deliberately carries no `categories` (Decision AY `architecture.md:3312`). Adding a count field to `ModelSummary` would change a shipped response consumed by every catalogue surface for one admin panel — the opposite of minimal. A narrow admin-only read leaves every public contract byte-unchanged.

**Why `min_categories` is a param and not a server constant.** The operative product value is the **frontend** constant (D-2); the server default of `4` exists so a direct API caller gets the documented norm, and a backend test pins it so a drift between the two becomes visible rather than silent. The frontend always sends the value explicitly.

**What was rejected, with reasons recorded:** per-category enumeration client-side (O(categories) requests; silently wrong above the 200-row page cap — §2); one `GET /api/models/{id}` per queue row (N+1, and the queue is the wrong corpus anyway); adding `categories` or `category_count` to `ModelSummary` (retracts a ratified decision, changes a public contract for an admin-only reader); a six-check aggregate `GET /api/admin/curation-qa` endpoint (would move five already-satisfiable checks to the server and duplicate data the page holds — larger contract, no gain).

### D-2 — The threshold: **> 3 flags** (i.e. ≥ 4), **tiny = 1–2**, **empty = 0** — confirmed, with a named re-evaluation trigger

The epic sketch requires "a **concrete number** … rather than inherit the vagueness" (readiness finding m-2). The UX artifact supplies `> 3` / `1–2` as an inherited default; this story **confirms** it, on four grounds that are checkable rather than aesthetic:

1. **It is already shipped product behaviour.** `ModelCategoriesDialog.tsx:27` ships `ADVISORY_MAX = 3` with bilingual copy behind `modules.admin.categories.editor.advisory`. A different number in 52.3 would put two surfaces **on the same page** in disagreement: the replace-set editor would accept a set without warning while the QA panel flags the same model. That is a defect the number choice can simply avoid.
2. **It is the ratified requirement, not a preference.** FR26-CAT-3 states the norm as "1–3 categories per model". Picking 4 or 5 here would silently amend a ratified FR outside `bmad-correct-course`.
3. **It is proportionate to the shipped vocabulary.** The seed ships **eight** flat categories (`seed.py:288-356`). "More than 3" means a model occupying **more than 37.5%** of the entire browse vocabulary — at that density the category axis has stopped discriminating, which is precisely the drift the check exists to catch.
4. **`tiny = 1–2` is the complement of the admission bar, not a new number.** FR26-GOV-1 requires evidence a category is "a useful entry point for **multiple** models", and Story 49.2 owes a distribution check that each category "would land **≥ 3** models". A category below that bar is by definition one that would not be admitted today — which is exactly "behaving like a narrow tag".

**Named re-evaluation trigger (recorded, not a deferral):** ground (3) is a ratio argument against an eight-category vocabulary. If the vocabulary grows past roughly **16** categories, ">3" stops meaning "most of the taxonomy" and the norm should be re-derived — at that point via `bmad-correct-course` against FR26-CAT-3, never by editing the constant in place. Until then, 3 stands.

**Mechanically enforced as one constant.** The value moves to a new non-component module `apps/web/src/modules/admin/curationThresholds.ts` exporting `ADVISORY_MAX = 3` and `TINY_MAX = 2`; `ModelCategoriesDialog.tsx` imports it instead of declaring it locally. This is a two-line change to a shipped file with **no behaviour change**, and it is justified rather than stylistic: the alternative is two independent `3`s. It cannot be an export from `ModelCategoriesDialog.tsx` itself — `react-refresh/only-export-components` is a `warn` under `--max-warnings=0` (`project-context.md:130`), so a non-component export from a component file fails lint. Precedent for a sibling helper module in this folder: `duplicateTags.ts`.

### D-3 — Six checks, no seventh; "behaving like a narrow tag" is a diagnosis, not a check

`epics.md:4561` lists "empty/tiny categories; categories behaving like narrow tags" as if they were separate. `EXPERIENCE.md:233` resolves it: the six checks are (1) zero-category model, (2) `> ADVISORY_MAX` categories model, (3) empty category, (4) tiny category (`model_count` 1–2), (5) Category/Tag label collision, (6) ungrouped user-facing tag. The mockup's own caption ties "behaving like a narrow tag" to the **tiny-category** row and the label collision beside it — it is what the admin *concludes* from checks 4 and 5, not a seventh detector. **Do not invent a seventh check.**

### D-4 — Label collision reuses the shipped similarity, and never crosses languages

Check 5 compares each category label against each tag label using `duplicateTags.ts`'s shipped rules, unchanged:

- Normalize with the exported `normalizeTagText` (NFD, `ł/Ł` map, lowercase, trim, whitespace collapse).
- Compare **en-vs-en and pl-vs-pl independently**, never en-vs-pl — the deliberate rule `tagsSimilar` (`duplicateTags.ts:73-90`) already records.
- Compare only when **both** sides are non-empty, so a null or empty `name_pl` never produces a finding.
- Similarity is the shipped length-scaled Levenshtein (`≤4` chars → exact only; `≤8` → distance 1; longer → distance 2), reached by **exporting** the existing `fieldsSimilar`. Authoring a second similarity notion for the same product concept is the "reinventing wheels" failure this story is written to prevent.

Each finding names the category label, the tag label, **and the tag's group label** (`EXPERIENCE.md:477`: „kategoria „Wazony" / tag „Wazony" (Typ)"), resolved from the same `useTagGroups()` payload. A **groupless** tag renders with no group suffix — never a placeholder (the `EXPERIENCE.md:225` rule for the suggestion pill, applied consistently here).

### D-5 — The panel is advisory in the strongest sense: it performs no write, ever

Every row is `⚠ marker + finding + affected entity + a link to the fix` (`EXPERIENCE.md:233`). The link either navigates (`/admin/tag-groups`, in-page anchor to the shipped queue) or opens a **shipped** 52.2 dialog (the replace-set editor, the category row's menu target). The panel itself issues no mutation, holds no mutation hook, and offers no bulk action. It deliberately **does not** copy `DuplicateTagsPanel`'s `onMergeCluster`.

No suggestion is auto-applied and no category membership is ever inferred from tags (`EXPERIENCE.md:290`, FR26-ADMIN-2). Concretely forbidden: "these tags suggest this category", "assign all", "merge into", "fix all".

### D-6 — The panel must never fabricate a green "Nothing needs attention"

This is the direct carry-forward of the 52.2 native-review defects R-3 and R-4 (a queue that discarded valid cached rows on a background-refetch error, and one that rendered a green empty state while still loading). The panel reads **four** sources: `useAdminCategories()`, the shipped `uncategorized` models query, `useTagGroups()`, and B-1's hook. Therefore:

- **Unresolved** (any source has no data and no error yet) → `aria-hidden` pulse skeleton, no count, no empty state.
- **Errored with cached data present** → compute and render from the cache; the panel does not blank (`TagGroupsPage.tsx:491-493` stale-while-error convention, which `CategoriesPage.tsx:296-297` already follows for its own list).
- **Errored with no data** → render every finding the *other* sources could compute, **plus** an explicit line naming that some checks could not run, with a retry. The "Nothing needs attention." empty state renders **only** when all four sources resolved successfully and produced zero findings.

### D-7 — Deterministic row order, deliberately not the mockup's row order

Mockup frame 2 renders its six rows in a narrative order chosen to tell Flow 3's story. A visual baseline needs a total order that does not depend on which finding happens to exist. This story fixes the order as: **(a)** empty categories, **(b)** tiny categories, **(c)** label collisions, **(d)** over-categorized models, **(e)** the uncategorized-models count row, **(f)** the ungrouped-tags count row — category-level findings, then cross-entity, then model-level, then the two aggregates. Within (a)/(b) the server's `(position, slug)` order; within (c) `(category position, tag name)`; within (d) B-1's `(category_count DESC, slug ASC)`.

This is a **recorded deviation** from the mockup's row sequence, on determinism grounds. The mockup's *content* contract — marker, finding, sub-line, fix link — is followed exactly.

### D-8 — Bounded rows with an honest overflow line

The two per-entity list checks can in principle produce many rows. The panel renders at most **5** rows per check and, when there are more, a non-interactive overflow line stating the true remaining count (`total` from B-1 for check (d); the derived array length for the others). The *pattern* mirrors the shipped suggestion-overflow-note rule (`EXPERIENCE.md:226`): the cap must never read as "these are all of them". The heading count is the count of **findings**, not of rendered rows.

**What the number 5 points to** (`project-context.md:287` — a numeric constant in an AC must point at the contract it serves, not at another place the number appears). The UX artifact fixes **no** row cap for this surface, so 5 is this story's choice and is justified here rather than inherited. The contract it serves is **AC-8's mount position**: the panel sits between the page `<header>` and the category list, so it is an advisory *preface* to the primary surface, never the surface itself. Against the shipped eight-category vocabulary (§2), six checks × 5 rows is already a worst case that fills a viewport; letting any single check run unbounded would push the category list — the thing the panel is advising about — below the fold, inverting `DESIGN.md:284`'s advisory-not-primary posture. Deliberately **not** aligned to the suggestion panel's 8-row cap: that cap is sized for a single-purpose listbox that owns its whole popover, which is a different constraint, and matching it would be the "it matches the other place it appears" category error the rule forbids. **Named re-evaluation trigger:** if the panel is ever given its own route or a collapsed/expanded affordance, the mount-position argument dissolves and the cap should be re-derived — not edited in place.

### D-9 — Query keys, invalidation, and the four-source cache-coherence table

B-1's hook uses `["sot", "admin-categories", "over-categorized", minCategories]` — a **child** of the shipped `ADMIN_KEY = ["sot","admin-categories"]` (`useAdminCategories.ts:14`). This is deliberate and is the opposite call from 52.2 D-12's sibling decision, for a reason that inverts: there, a child of the **public** key would have made every member's browse rail refetch an admin-only endpoint; here the parent is already admin-only, and every write that changes a model's category count already invalidates `ADMIN_KEY` through the shared `invalidateCategories(qc)` helper — verified at `useAdminCategories.ts:99` (`useDeleteBrowseCategory`, incl. `detach=true`) and `:120` (`useReplaceModelCategories`) — so the prefix sweep reaches the child for free and costs no new invalidation code.

**Cache-coherence enumeration (mandatory per `project-context.md:286`; this is the Init 18 TB-050 discipline).** The panel is a *single rendered claim* composed from four independently-cached sources. Their shipped staleness budgets diverge by 30×, so the table is filled for all four, not just the new one:

| Source | Key | staleTime | Retry | Propagation on admin writes | Eviction on route exit | Seeding on this route |
|---|---|---|---|---|---|---|
| `useAdminCategories()` — checks (a)(b)(c) | `["sot","admin-categories"]` | **10 s** (shipped, `:24-26`) | shipped default | `invalidateCategories` on all 4 category writes | none (shared cache, deliberate) | already mounted at `CategoriesPage.tsx:139` |

**The one place the columns disagree, and the call.** `useTagGroups()` at 5 min sits beside `useAdminCategories()` at 10 s.
