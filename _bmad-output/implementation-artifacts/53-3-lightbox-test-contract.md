## 3. Design decisions

### D-1 — This is a test-contract story **plus two bounded product repairs**, and that is deliberate

`epics.md:4579` reads as pure test authoring. It is not, and pretending otherwise would leave two shipped defects unowned:

| Deferred at 53.2 CR | Assigned to | Why it cannot be "just a test" |
|---|---|---|
| `/share` renderer that never mounts an `<img>` → toolbar disabled forever, failure never announced | **53.3** (`deferred-work.md`, verbatim) | Needs a readiness **timeout** — new constant, new behaviour (D-5). A test alone would only document the defect. |
| `imageStatus === "error"` renders an empty live region; no inline error element | **53.3** (`deferred-work.md`: *"**53.3** owns closing it (one new key in both `en.json` and `pl.json`, plus the inline element)"*) | Needs the element and the key (D-6). |
| Double-tap flashes the chrome layer on every zoom | **NOT 53.3** | The only fix defers *every* short tap by 300 ms, which violates 53.2 AC-3's guarantee that TB-043's four-cell matrix at scale 1.0 stays behaviourally identical. **Stays deferred; needs an AC-3 amendment via `bmad-correct-course`.** Do not "fix" it here. |
| `DOUBLE_TAP_WINDOW_MS` / `DOUBLE_TAP_SLOP_PX` boundaries unconstrained | **53.3** | Pure test work (D-9). |

Consequence: this story touches product code in exactly **two** places (`ImageFullscreenViewer.tsx`, plus one key in each locale file) and is otherwise tests. Every other file it touches is a test file. AC-9 makes that a mechanical check.

### D-2 — Landscape and rotation come from an axis swap of the project's own viewport

```ts
async function rotate(page: Page) {
  const vp = page.viewportSize();
  if (vp === null) throw new Error("no viewport");
  await page.setViewportSize({ width: vp.height, height: vp.width });
}
```

- **Landscape coverage:** navigate → `rotate(page)` → open the viewer. The viewer mounts into a landscape viewport.
- **Rotation refit:** open the viewer → `rotate(page)` → assert.
- **Skip on `desktop-*`:** `test.skip(!testInfo.project.name.startsWith("mobile-"), "…")`, the `image-viewer-containment.spec.ts:260` idiom. Rotating a desktop Chrome window is not a phone rotation and would assert nothing about `epics.md:4579`'s "Pixel 5 landscape".
- **Rejected alternative:** `test.use({ viewport: { width: 851, height: 393 } })` (the `settings-profile.spec.ts:38` shape). It requires literal numbers duplicated out of Playwright's `devices["Pixel 5"]` descriptor, which rots silently on a Playwright bump — and it cannot express the rotation case at all.
- **Rejected alternative:** a fifth Playwright project. The 4-project matrix is fixed (V-3, `project-context.md:110`); widening it re-baselines the whole suite.

### D-3 — The geometry matrix is written **inside** `image-viewer-containment.spec.ts`. No new spec file, no extraction.

V-6 is decisive: the PNG generator, `openViewerWith`, `boxOf`, `expectWithinViewport`, `expectContainedBy`, `assertContained` and `assertDismissible` are **all** file-local to that suite. There are three ways to get at them and only one is sound:

| Option | Verdict |
|---|---|
| **Extend that file in place** | ✅ **Chosen.** Zero duplication, zero extraction risk, and V-2 already assigns *"extending that suite"* to this story. The file is exactly the geometry-containment concern the new tests belong to. |
| Extract the helpers into a shared module, import from a new spec | ❌ Rejected. It rewrites a **standing regression suite** (`architecture.md:3376`) for zero functional gain — the diff churn lands on the one file whose job is to be a stable witness. Minimal-diff policy applies. |
| Copy the helpers into a new spec | ❌ Rejected. ~130 duplicated lines of CRC32/PNG encoder and geometry assertions, in a story whose whole point is not letting this component drift. |

**Constraints on the extension (AC-9):**
- The four existing `test(...)` bodies stay **byte-identical**.
- Helper changes are **additive only**: new helpers, or new *optional* parameters with today's behaviour as the default (`openViewerWith` gains an orientation option; its existing three call sites are untouched).
- The suite still produces **no snapshots**. If a baseline appears, something was added that does not belong here.
- Fixture sizes come from D-4; reuse `EXTREME_TALL` (1200×6000) for the portrait-1:4 case if the dev judges a fourth fixture redundant, and say so in the record.

**Escape hatch, not a default:** if a *later* surface genuinely needs `solidPng` outside this file, extract it then, as pure code motion with a diff proving every test body unchanged. Do not pre-emptively extract for a consumer that does not exist.

### D-4 — Fixture aspect ratios, stated as concrete numbers with a contract each

`epics.md:4579` names the ratios but not the pixel sizes. Ruling, so the dev agent does not invent them:

| Case | Size | Contract |
|---|---|---|
| **Panorama 4:1** | `4000 × 1000` | Wide enough that a Pixel-5-class frame downscales it hard, so `resolveMaxScale` returns the native-pixel ratio rather than `BASE_MAX_SCALE` — i.e. the branch `zoom.test.ts:53` covers algebraically is exercised through real layout. |
| **Panorama 8:1** | `8000 × 1000` | The inspectability case `FR26-VIEW-1` exists for. Also the widest thing the `max-h-[calc(95dvh-5rem)]` cap must survive in **landscape**, where vertical budget is scarcest. |

| **Small source** | `120 × 90` | Smaller than the rendered frame in every project. Proves `resolveMaxScale` falls back to `BASE_MAX_SCALE = 4` (rather than a sub-1 ratio) so the three controls are not dead — the exact case 53.2's `max(4, ratio)` reading was chosen to protect (`53-2:438`). |

All four deflate to a few KB (all-zero greyscale), as `image-viewer-containment.spec.ts:61-65` documents. If a number turns out wrong on evidence, changing it is fine; changing it **silently** is not — record it in the Change Log with the contract it now serves (`project-context.md` § "Magic constants in specs require contract-pointing justification").

### D-5 — The readiness timeout: mechanism, constant, and its contract

**Mechanism.** In the same effect that installs the capture-phase `load`/`error` listeners (`ImageFullscreenViewer.tsx:340-400`), arm a timer whenever the resolved status is `loading`. On fire → `setImageStatus("error")`. Clear it on: a `load` event, an `error` event, an `activeIdx` change, and unmount. **A late `load` after the timeout fired must still flip the state back to `ready`** — the timeout reports a stall, it does not permanently condemn the image.

**Where it is tested — vitest, not Playwright (V-21).** The defect is a property of the component's own prop boundary: a `renderImage` that returns something without an `<img>` in it. Mount the viewer with `renderImage={({ alt }) => <div aria-label={alt} />}`, advance fake timers past `IMAGE_READY_TIMEOUT_MS`, assert the error state. One line of fixture versus a whole `/share` Playwright harness that no spec has ever needed. **Do not build the `/share` harness for this.**

**Constant.** `IMAGE_READY_TIMEOUT_MS = 15_000`, declared alongside the other viewer constants (`:76-93`) with its contract in a comment.

**Its contract, stated (V-13):**
1. It must **never** fire on a legitimately slow path. The floor is set by `shareBlobCache`'s `MAX_CONCURRENT_FETCHES = 4` semaphore: on a share view with a large strip, an image's fetch can sit **queued** behind several batches before it is even dispatched, and nothing below it has a timeout of its own.
2. It must fire **well inside** the window where a user reads total silence as "broken". 15 s is far above (1) on any working connection and far below the indefinite wait that is today's behaviour.
3. It is **not** a latency SLO. Do not tune it to make a slow test faster, and do not add a retry — retry policy belongs to `shareBlobCache`, which owns the rate-limit and semaphore invariants (V-12/V-13) and which this story **must not touch**.

**Test technique:** the timer is real, so drive it with vitest fake timers in the component test rather than a 15 s Playwright wait. The Playwright slow-load case uses a *short* delayed `route.fulfill` and asserts the **disabled-then-enabled** transition, which needs no timeout at all.

### D-9 — Double-tap window/slop boundaries: solve `timeStamp` once

`fireEvent` cannot set `timeStamp` (V-18). Construct the event and override before dispatch, in **one** helper reused by every boundary case:

```ts
function touchEndAt(el: Element, at: number, x: number, y: number) {
  const touch = new Touch({ identifier: 1, target: el, clientX: x, clientY: y });
  const ev = new TouchEvent("touchend", { bubbles: true, touches: [], targetTouches: [], changedTouches: [touch] });
  Object.defineProperty(ev, "timeStamp", { value: at });
  fireEvent(el, ev);
}
```

Four cases, each pinning one comparison: inside the window → double-tap; **just outside** it → two single taps; inside the slop → double-tap; **just outside** the slop → two single taps. `TouchEvent` / `Touch` construction in jsdom follows the shape 53.2 established for Chromium (`53-2:430`) — object literals are rejected there and the same discipline keeps one idiom across both runners.

**AC-3 — Rotation refits without clipping and without losing the user's zoom.**
Given the viewer is open and zoomed above 1.0 with a non-zero pan, when the viewport axes are swapped (D-2), then the zoom **level is preserved**, pan is **re-clamped** so no image edge sits inside the frame edge, the image and every control remain inside the visual viewport, and no document overflow appears (`EXPERIENCE.md:262`). **AC-4 — Zoom and pan clamp and reset, measured at real layout.**

Pure algebra stays in `zoom.test.ts` (V-11); this AC is about the wiring.

### Current state of the code being modified

`ImageFullscreenViewer.tsx` (1056 lines at `933013e`) is a three-layer structure inside a Base UI `Dialog`: the **transform layer** (`:826-852`, `touch-none`, `translate3d(...) scale(...)`, wrapping whatever `renderImage` returns); the **chrome layer** (`:858-922`, fades and goes `aria-hidden` on `chromeVisible`, holding counter / close / chevrons); and the **toolbar layer** (`:942-1000`, a sibling of the chrome layer — always mounted, never `aria-hidden`, carrying the polite zoom-level region and the three 40 px controls). ### Implementation traps verified this run

- **jsdom has no layout.** `getBoundingClientRect()` is all-zero and there is no `scrollIntoView`. A clamp test written naively against jsdom rects passes trivially and proves nothing — the "lying about completion" failure mode. Real geometry belongs in Playwright; jsdom keeps state transitions, ARIA and timing.
- **`TouchEvent` construction.** Chromium rejects object literals in `touches`/`changedTouches`; use `new Touch({ identifier, target, clientX, clientY })` (`53-2:430`). Keep the same idiom in jsdom (D-9) so there is one technique, not two.
- **React registers `touchstart` / `touchmove` / `wheel` as PASSIVE** at the root (read out of the installed `react-dom` 19.2.6 bundle — `53-2:72`). `preventDefault()` from a React touch handler is a no-op. This story adds no gesture handling, but a test that assumes a default was prevented will assert a fiction.
- **`page.mouse.wheel` is the only honest scroll-lock probe.** `overflow: hidden` suppresses *user* scrolling but still permits *programmatic* scrolling; `window.scrollTo` passes vacuously (`53-2:431`).
- **Scroll-lock target is platform-dependent.** Real Chromium locks `<body>` alone; jsdom sets both. Keep AC-7's assertions **element-agnostic**, as the shipped test already is (`53-2:433`).
- **Live-region announcements do not fire on insertion.** An `aria-live` region does not announce content it is *inserted with*, and Base UI portals the subtree in at once — the announcement must live in state and be written from an effect (`53-2:291`). D-6's error announcement inherits this.
- **`vitest` runs with `globals: false`** — every test file owns its `afterEach(cleanup)`. The existing viewer test file already does; keep it that way.
- **Visual Coverage Contract.** `_check-visual-coverage.mjs` only fires on newly **added** `apps/web/src/ui/*.tsx`. Nothing in this story adds one; keep the error element inside the module component and the hook never fires.
- **A real timer inside a jsdom suite is a cross-test hazard.** `IMAGE_READY_TIMEOUT_MS` arms on every mount where the image has not resolved — which, in jsdom, is *every* existing viewer test, because jsdom never fetches and never fires `load`. The timer is cleared on unmount, so the default path is safe; the hazard is any test that installs fake timers and advances them far enough to trip it, silently flipping `imageStatus` to `error` mid-assertion. After the timer lands, **re-run the whole `imageViewer/` vitest suite**, not just the new cases — this is the masked-test class `project-context.md` § "Test discipline — hang/timeout class bugs" was written for.

### 14.2 DN-4 — the decision-needed item

**The readiness watchdog never arms on `/share` after in-viewer navigation, and the viewer reports `ready` over an empty placeholder.**

**Mechanism.** `renderImage` is invoked as a **plain function** (`ImageFullscreenViewer.tsx:913`; `types.ts:23` types it `(props) => ReactElement`), and `/share` passes it **by reference** (`routes/share/$token.tsx:377` — `renderImage={AnonymousImage}`). `AnonymousImage`'s `useState` / `useEffect` (`$token.tsx:129-148`) therefore become hooks of the **viewer's own fiber**, registered *after* every hook in the viewer body — including the readiness effect. Passive effects on one fiber run in registration order, so on a next/prev press the readiness effect runs **first**, while `objectUrl` still holds the outgoing photo's blob URL and its `<img>` is still in the DOM. `frame.querySelector("img")` returns that stale element (`complete === true`, `naturalWidth > 0`), the probe takes the third branch (`:440-441`) → `setImageStatus("ready")` + `measureMaxScale(staleImg)`, and **`armReadyTimeout()` is never reached**. ```
